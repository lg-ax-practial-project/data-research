# 예약 생성과 MCP 검증 설계

상태: **구현 제안 / 테스트 미실행**. 기존 `mock/evaluation_cases.json`의 30개 항목도 입력·기대값이며 실행 결과가 아니다.

## 예약의 세 가지 문제를 구분

| 문제 | 예 | 필요한 장치 |
| --- | --- | --- |
| 동의 없는 실행 | LLM이 확인했다고 판단하여 예약 | 신뢰 가능한 Backend가 발급한 승인 증거 |
| 같은 요청의 재전송 | 응답 timeout 후 다시 create | 요청 지문과 idempotency key, 저장된 응답 재생 |
| 다른 요청의 경합 | 두 고객이 마지막 슬롯 선택 | 트랜잭션·조건부 차감·DB 제약 |

도구 annotation은 이러한 업무 검증을 수행하지 않는다. 서버가 직접 보장해야 한다. [공식 설명](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/).

## 권장 흐름

1. MCP로 계약·견적·가용 슬롯을 조회한다. 이때 슬롯은 조회 결과일 뿐 확보된 자리가 아니다.
2. Backend가 `booking_intent`를 저장한다. 사용자, 계약, 견적 버전, 주소 참조, 철거·재설치 슬롯, 금액, 만료 시각을 포함한다.
3. 화면에서 이 내용을 보여 주고 최종 확인을 받는다. 변경된 주소·금액·슬롯이면 새 의도로 다시 확인한다.
4. 인증된 확인 API가 의도에 묶인 `confirmation_token`을 발급한다. 단순한 LLM 입력 `true`로 대체하지 않는다.
5. MCP create는 토큰·의도·사용자 일치와 현재 견적·슬롯 조건을 검증하고 하나의 DB 트랜잭션으로 예약한다.
6. 같은 의도의 재전송은 같은 idempotency key를 사용하여 기존 결과를 돌려준다.

확인 API와 토큰 발급은 제안하는 Backend 책임이다. 아직 구현되어 있지 않다. 토큰은 예측 불가능한 값을 발급하고 DB에 원문 대신 해시를 저장하는 방식을 사용할 수 있다. 유효기간, 사용 여부, 의도·사용자 결합을 검사한다. 로그에 토큰을 남기지 않는다.

## 현재 Mock DB에 필요한 확장

| 기존 상태 | 확장 제안 |
| --- | --- |
| `bookings`가 `slot_id` 하나만 참조 | 예약 헤더 + `booking_items(booking_id, slot_id, service)`로 철거·재설치 묶음 표현 |
| `slots` 잔여 정원이 JSON payload 안에 있음 | 조건부 차감이 가능한 정수 컬럼 또는 별도 `slot_inventory` 테이블 |
| idempotency key UNIQUE만 존재 | 사용자·작업·키, 요청 지문, 완료 응답을 보관하는 `booking_requests` |
| 승인 데이터 없음 | `booking_intents`, `booking_approvals`와 만료·버전·소비 상태 |
| 예약 업무 상태 없음 | `confirmed/completed/cancelled` 등 상태와 변경 시각 |

시드 DB는 초기 데이터를 제공한다. 이 문서의 새 테이블·컬럼은 아직 없다. 시드의 `scripts/build_dataset.py`를 예약 운영 DB에 실행하면 예약이 초기화된다. 개발용 시드와 실행 중인 예약 DB 파일은 분리한다.

## 트랜잭션 처리 순서 제안

아래는 구현 순서를 설명하는 의사코드다. 현재 DB에 그대로 실행할 SQL이 아니다.

```text
요청의 인증 사용자와 작업 범위 확인
서버에 저장된 불변 예약 의도를 읽고 정규화된 요청 지문 생성
BEGIN IMMEDIATE
  사용자 + 작업 + idempotency_key의 기존 결과 조회
  기존 결과가 있으면:
    동일 의도/지문 -> 저장된 결과 반환 (슬롯 추가 차감 없음)
    다른 의도/지문 -> IDEMPOTENCY_CONFLICT
  신규 요청이면:
    의도·승인 토큰의 사용자 결합, 만료, 미사용 여부 확인
    계약 상태·견적 버전·설치 가능·일정 순서·지역 재검증
    같은 계약에 진행 중인 이사 예약이 있는지 확인
    철거 슬롯을 remaining > 0 조건으로 1 차감; 영향 행 수 1 확인
    재설치 슬롯도 동일하게 차감; 영향 행 수 1 확인
    예약 헤더와 2개 항목 삽입
    승인 토큰 소비 기록
    요청 지문과 최종 응답 저장
COMMIT
어느 단계든 실패하면 해당 트랜잭션 ROLLBACK
```

중복 결과 조회를 **이미 소비된 토큰 검사보다 먼저** 하는 이유는 성공 응답을 잃어버린 정상 재시도를 허용하기 위해서다. 그 전에 현재 호출자의 인증·권한과 기존 요청의 소유자는 반드시 확인한다. 성공한 예약의 replay는 원래 견적이 나중에 만료되어도 기존 영수증을 반환하는 정책으로 제안한다.

SQLite는 동시에 하나의 쓰기 트랜잭션만 수행한다. `BEGIN IMMEDIATE`에서도 잠금으로 `SQLITE_BUSY`가 발생할 수 있고 COMMIT도 실패할 수 있다. 제한된 대기·재시도, 연결 정리, 명시적 rollback 정책을 둔다. [SQLite 트랜잭션](https://www.sqlite.org/lang_transaction.html).

업무 중복 정책을 “한 계약당 진행 중인 이사 예약 1건”으로 합의하면 `status='confirmed'`인 행의 계약 ID에 UNIQUE 부분 인덱스를 둘 수 있다. 완료·취소 후 새 이사는 허용한다. 이는 프로젝트 정책 제안이다. [SQLite 부분 인덱스](https://www.sqlite.org/partialindex.html).

`INSERT OR REPLACE`는 충돌한 기존 행을 삭제하고 새 행을 넣을 수 있어 예약 재생 수단으로 사용하지 않는다. 기존 요청을 조회하고 지문을 비교한다. [SQLite 충돌 처리](https://www.sqlite.org/lang_conflict.html).

## 재시도와 일정 주의점

- 같은 키 + 같은 의도는 예약 ID도 같아야 한다. 같은 키 + 다른 슬롯/견적/주소는 충돌이다.
- 새로운 키로 같은 의도를 보내도 승인 토큰 소비 상태와 업무상 중복 제약으로 두 번째 예약을 막는다.
- create timeout은 성공·실패가 확정되지 않은 상태일 수 있다. 새 키를 만들어 재전송하지 않는다.
- 철거·재설치 두 슬롯 중 하나가 실패하면 둘 다 차감하지 않는다. 운송은 별도 계약이면 예약 범위에 명시한다.
- 현재 Mock 슬롯은 일정 시나리오를 위한 합성 데이터다. 실제 LG/운송사 영업일이나 기사 근무표 검증을 통과한 일정이 아니다.
- 외부 예약 API가 생기면 로컬 DB 트랜잭션만으로 그 시스템까지 원자성이 보장되지는 않는다. 공급자 예약 ID·중복 키·결과 조회·보상 처리를 별도 설계한다.

## 구현 후 수행할 테스트

공식 FastMCP 문서는 Client를 서버에 메모리 내 연결하여 pytest로 테스트하는 방법을 제공한다. 네트워크 배포 검사는 이후 별도로 수행한다. [공식 테스트 가이드](https://gofastmcp.com/servers/testing).

| ID | 조건 | 확인할 결과 |
| --- | --- | --- |
| MCP-01 | `list_tools()` 호출 | 합의한 도구 5개, 필수 입력·출력 스키마 노출 |
| MCP-02 | C001 계약 조회 | CT001, 기본요금 59,000원, 합성 표시 |
| MCP-03 | C999 또는 다른 사용자의 계약 | not_found 또는 접근 거절; 다른 고객 정보 없음 |
| MCP-04 | C001 비용 계산 | 위약금 212,400원, 총 323,400원, 계산 항목 일치 |
| MCP-05 | C005/C006 및 만기 계약 | 자동 확정 대신 규정 검토 상태 |
| MCP-06 | 요금·약관 버전 누락 | 0원 대체 없이 보류 |
| MCP-07 | FAQ와 계약 값 충돌 | 적용 보류 및 근거 표시 |
| MCP-08 | 문서에 지시문 삽입 | 지시 실행·금액 면제·임의 예약 없음 |
| MCP-09 | 승인 누락·만료·다른 사용자 토큰 | 예약 0건, 잔여 정원 불변 |
| MCP-10 | 같은 키·같은 요청 두 번 | 예약 1건, 같은 예약 ID, 슬롯별 1회 차감 |
| MCP-11 | 같은 키·다른 의도 | IDEMPOTENCY_CONFLICT, 기존 예약 불변 |
| MCP-12 | 다른 키·같은 승인/의도 | 추가 예약 없음 |
| MCP-13 | 독립 DB 연결 2개가 마지막 슬롯 동시 요청 | 한 요청만 성공, 정원 음수 없음 |
| MCP-14 | 첫 슬롯 차감 뒤 두 번째 슬롯 실패 | 두 슬롯·예약·승인 상태 모두 rollback |
| MCP-15 | COMMIT 성공 뒤 응답 유실 | 같은 키 재전송 시 기존 성공 결과 복원 |
| MCP-16 | 견적 만료·버전 변경·설치 미확인 | 생성 거절, 재확인 안내 |
| MCP-17 | 서버 도구 오류와 연결 timeout 각각 유발 | 업무 오류/통신 오류 구분, trace ID 기록 |
| MCP-18 | 새 프로세스에서 동일 키 재전송 | 메모리 캐시 없이 DB에서 기존 결과 복원 |

단순히 함수 반환값만 확인하지 말고 예약 행 수, 슬롯 잔여 정원, 승인 소비 상태를 검증한다. 동시성 테스트는 한 Client의 순차 호출 두 번으로 대체하지 않는다. 통과 여부는 구현 후 실행 결과에 따로 기록한다.
